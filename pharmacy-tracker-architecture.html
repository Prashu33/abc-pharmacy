Medicine Tracker System Design

A single-page application backed by an ASP.NET Core Web API, storing inventory and sales data as JSON — designed for clarity, testability, and a clean upgrade path to a real database later.

00Overview

The system tracks medicine inventory and records sales. It exposes a small, focused REST API and a single-page front end that renders inventory as a color-coded grid — red for medicines expiring soon, yellow for low stock — with name-based search.

The design favors a thin, layered backend (Controller → Service → Repository) over a monolithic controller, so that expiry/stock business rules live in one testable place, and the JSON file storage can be swapped for SQL Server / EF Core later by replacing only the repository layer.

01Architecture

The API also serves the SPA's static files from wwwroot, so the whole app runs as a single deployable process — no CORS configuration, no second web server, one thing to build and submit.

Why one project, not two: a reviewer running this assessment should be able to dotnet run once and see the working app. Splitting API and SPA into separate servers only adds CORS setup and a second start command for no functional benefit here.

03Domain Models

The list endpoint returns a dedicated DTO that excludes Notes and includes pre-computed color flags — the grid requirement is satisfied literally, and the color logic lives in the backend, not duplicated in JavaScript.

// Models/Medicine.cs
public class Medicine
{
    public Guid Id { get; set; }
    public string FullName { get; set; }
    public string Notes { get; set; }
    public DateTime ExpiryDate { get; set; }
    public int Quantity { get; set; }
    public decimal Price { get; set; }      // stored to 2dp, enforced in DTO validation
    public string Brand { get; set; }
}

// Models/SaleRecord.cs
public class SaleRecord
{
    public Guid Id { get; set; }
    public Guid MedicineId { get; set; }
    public int QuantitySold { get; set; }
    public decimal UnitPriceAtSale { get; set; }
    public decimal TotalAmount { get; set; }
    public DateTime SaleDate { get; set; }
}

// Models/Dtos/MedicineListDto.cs — used only by the grid endpoint
public class MedicineListDto
{
    public Guid Id { get; set; }
    public string FullName { get; set; }
    public DateTime ExpiryDate { get; set; }
    public int Quantity { get; set; }
    public decimal Price { get; set; }
    public string Brand { get; set; }
    public bool IsNearExpiry { get; set; }   // < 30 days → red
    public bool IsLowStock { get; set; }    // < 10 units → yellow
}

04JSON Storage Layer

Wrapped behind IJsonRepository<T> so persistence can be swapped for a real database later without touching controllers or services.

Concurrency

A SemaphoreSlim per repository instance guards every read/write, since two overlapping API requests could otherwise corrupt the file.

Durability

Writes go to a temp file first, then File.Move replaces the original — an atomic swap that avoids partial writes if the process is interrupted.

// Repositories/IJsonRepository.cs
public interface IJsonRepository<T>
{
    Task<List<T>> GetAllAsync();
    Task<T?> GetByIdAsync(Guid id);
    Task AddAsync(T entity);
    Task UpdateAsync(T entity);
}

Serialization uses System.Text.Json with camelCase naming, so the JSON on disk matches what the JavaScript front end expects without a mapping layer.

05API Contract

MethodRoutePurpose
GET/api/medicines?search=Grid list (no Notes); optional case-insensitive name filter
GET/api/medicines/{id}Full detail, including Notes — for an edit/detail view
POST/api/medicinesAdd a medicine (validates Price, Quantity, ExpiryDate)
POST/api/salesRecord a sale; decrements stock and appends a SaleRecord
GET/api/salesSale history (supports the "maintain sale records" requirement)
Sale flow matters here: recording a sale isn't just an append to sales.json — inside the same locked operation, SaleService checks available stock, rejects the request if quantity sold exceeds stock on hand, then decrements Medicine.Quantity so the grid and the sale ledger never disagree.

06Business Rules & Grid Preview

Color flags are computed once, server-side, in MedicineService — the front end only reads isNearExpiry / isLowStock and applies a CSS class. This keeps the 30-day and 10-unit thresholds in one testable place instead of scattered across JS.

08Cross-Cutting Concerns

  • Validation — DataAnnotations/FluentValidation on DTOs: required fields, Price > 0, Quantity ≥ 0, ExpiryDate sanity checks.
  • Error handling — a global exception middleware returns a consistent JSON error shape: { message, errors }.
  • API documentation — Swagger/OpenAPI enabled in Program.cs for quick manual testing.
  • Unit tests — xUnit coverage for the expiry/low-stock flag logic and the sale stock-decrement logic, since these are the two rules the assessment is actually graded on.
  • Configuration — JSON file paths read from appsettings.json, never hardcoded.
